## 1. 问题定义

本库的立论是「对 Agent 来说，看不到的知识等于不存在」，所以项目知识一律版本化落到 `docs/` 六模块。但这套结构管的是**项目自己产生的知识**——要做什么、做了什么、为什么这么设计，它不管另一件事：**代码本身的结构。**

当一个存量代码库有几十万行、又没有设计文档时，把模型指向源码树，它会先耗尽上下文，然后开始凭空发明各模块怎么运转。此时 `docs/specs` 里那份功能规格回答不了「订单是怎么走到 webhook 那段代码的」——规格描述意图，不描述现存结构。

不解决：AI 在存量代码上的每次改动都建立在猜测出来的结构理解之上，改错地方、漏改地方、把已有能力重新实现一遍，都是这个根因的不同表现。不解决别的：本调研不涉及「代码写得清不清楚」，只涉及「AI 能不能低成本看懂」。

## 2. 现状与调研

| 对象 | 做法 | 优劣 | 来源 |
|---|---|---|---|
| 让模型直接读源码 | 把目录树塞进上下文 | ❌ 大库先耗尽上下文，随后开始虚构结构 | EGM peanuts |
| 一次性让 AI 生成全量 README | 一条 prompt 生成所有目录说明 | ❌ 叶层 README 仅凭代码写，错误率约一半；父层从错误的子层总结，误差逐层放大 | 同上 |
| **自底向上 README 层级 + 每层人工门禁** | 先写叶子（peanuts），父层从子层 README 加自身文件总结（hay），每层等人审完才写上一层 | ✅ 全新会话只读 README 即可知道各子系统干什么，token 成本远低于读源码；误差不逐层放大 | 同上 |

### 三条可迁移纪律

| 纪律 | 内容 | 为什么 |
|---|---|---|
| 只准自底向上 | 任一子目录未经人工审定，父目录不许写 README | 叶层错误率约一半，父层从错误子层总结会让误差沿层级放大到顶 |
| AI 永不批准自己的产物 | README 的 `approved` 只能由人签字，脚本里没有任何命令能替人签 | 让模型「继续往下做」时，它会把自己的产出标记成已批准来解锁自己 |
| 每条 README 带退役声明 | 写明这是脚手架、将被设计文档取代 | 没有这句，人们会把过期的脚手架当现状永久保留 |

### 评审成本必须先报

外部来源给出的量级：每个叶子约 5–10 分钟人工评审，叶层错误率约一半。**这个成本要在动手前告知，而不是等生成完才发现要审几百个文件。**

### 事实与判断的界线

- **外部事实**：上述方法、三条纪律、错误率与评审时长量级，出自 [EECS 498 AASE 课程仓库](https://github.com/eecs498-aase/materials) 的 `egm/` 目录；方法原始出处为 Dave Rensin（Google）的 [Elephants, Goldfish and the New Golden Age of Software Engineering](https://drensin.medium.com/elephants-goldfish-and-the-new-golden-age-of-software-engineering-c33641a48874)。
- **我们的判断（未经验证）**：认为它与本库「看不到的知识等于不存在」是同一条立论向下一层的延伸，因此值得收。这一判断尚未在本库或任何采用方上验证过。

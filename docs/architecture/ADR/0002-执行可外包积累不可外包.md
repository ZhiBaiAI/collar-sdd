## 背景

接入 AI Agent 做研发后，一个团队要决定：哪些东西买现成的，哪些必须留在自己手里。
Agent 执行结构（跑任务、调模型、接系统）属于工程基础设施，完全可以采购、租用或由外部团队构建；
今天花大价钱买来的模型能力，随基座升级而贬值，买来的通用能力构不成任何团队的壁垒。

真正稀缺且无法外购的，是团队在一次次真实交付中积累的经验、判断标准与运行机制——
它们必须沉淀在团队自己的系统边界内，由团队自己拥有，才会随时间复利增长。
本项目（Collar SDD）的立身之本正是这件事：六模块知识库 + 入口地图 + 门禁，
把「项目自述」变成可被 AI 会话消费的资产。

两个反例印证方向：
天猫数字员工把「业务认知从组织维度沉淀成可复用资产」列为区别于编码工具的核心视角，
其上下文层（知识 / 能力 / 过程 / 协作四维资产）全部由研发副产物自动沉淀——
模型可换、框架可换，企业自己沉下来的上下文换不掉；
而协作类打扰的频率本身就是知识资产缺口的度量——agent 因知识缺口去找人，答案沉回知识资产，下次同类缺口就不再打扰任何人。

## 决策

**我们把「Agent 执行结构」划为可替换层，把「项目知识库」划为不可外包层。**

- 执行结构（Agent 框架、模型、工具、脚本）按「平台能力会被框架持续吸收、优先依赖平台不重复实现」的归属分层原则处理，允许随工具演进整体更换。
- 知识库六模块（specs / changelog / architecture / runbook / vendor / wiki）是本项目的资产本体：
  任何一次交付产生的判断、踩坑与约定，按提交关卡沉淀进对应模块；
  换 AI 工具、换模型、换编排框架，都不得成为知识库迁移或废弃的理由——知识库格式与 AI 工具解耦（Skill 目录放项目根、clone 即可用，见 `skills/README.md`）。

## 备选方案

| 方案 | 优势 | 代价 |
|---|---|---|
| 执行外包 + 积累自建（选定） | 跟进模型与工具进步；判断与经验随交付复利 | 需要维护知识库纪律（提交关卡、行数守卫、缝合协议） |
| 全部自建（含 Agent 执行结构） | 完全可控 | 平台能力被框架持续吸收，重复实现注定腐烂 |
| 全部采购（知识也放 SaaS） | 起步最快 | 上下文与判断沉淀在供应商边界内，随合同流失；离职与换商即清零 |

## 理由

- 模型每半年换代、工具每月迭代；知识沉淀越早越厚、越晚动手越贵（天猫的内部改造顺位判据：假设全链路每个节点都必须由 AI 完成，推不动的地方就是该先动的地方）。
- 「责任」无法外包：闯了祸兜底的永远是人；事实沉进资产、判断留给被路由到的人、责任由人兜底——这三条边界要求资产必须在自有边界内可审计。
- 本仓库同时是模板与示例：如果连模板都把知识放在外部工具里，下游项目没有任何理由相信「clone 即用」。

## 后果

- **正面**：知识库成为项目最不易贬值的部分；换工具的成本被限定在软链与配置层。
- **负面**：知识库纪律本身有维护成本（提交关卡、行数守卫、月度审计）。
- **必须接受的代价**：一部分通用知识（Agent 工程规范）不进本仓库，放 `agent-dev-skills`——本仓库只存与本项目相关的结论。
- **上下文影响**：无风险。本次决策把「为什么知识库必须自建」显式落盘，反而补上了此前只可意会的一条。

## Revisit 条件

- 出现可携带、可验证的「知识库标准格式」行业标准（类比 lockfile 生态），届时评估把六模块迁移到该格式。
- 平台方提供与本地 git 同等粒度的知识资产导出与审计能力，可重新评估「积累不外包」的边界。

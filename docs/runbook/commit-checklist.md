# 提交检查清单（按档使用）

> `scripts/hooks/pre-commit` 已自动拦截结构门禁、写边界与 `commit` 档质量门禁。
> **不再要求在 commit message 末尾粘贴 `1✅..7✅` 打卡**——把精力留在真正需要语义判断的条目上。

---

## Minor 小改（修 bug / 文案 / 局部重构）

只需确认两项（均由工具和命令给出客观结果）：
- [ ] 已跑 `fast` 档验证（改动文件 lint + 关联测试），且未通过吞异常/放宽断言做假修复
- [ ] `git commit` 顺利通过 `pre-commit` 与 `commit-msg` 钩子

---

## Standard / Major 改动（新功能 / 契约或架构变更）

在 Minor 基础上，按需过完以下 4 项语义检查：

### ① 意图与差异（`collar-specs`）
- [ ] 对应精简 `spec.md`（或 `patch`）的 `AC-N` 已覆盖核心可观测结果；未自动反向修改既有 Spec
- [ ] 若代码偏离 Spec，已输出差异清单并经确认

### ② 改动收敛与真值验证
- [ ] 无无关重构；因改动失效的死代码、旧接口与兼容层已同步删除
- [ ] 关键路径有真实命令/状态证据；Major 改动或发版前已跑 `release` 档全量验证

### ③ 架构与上下文缝补（仅涉及结构/外置逻辑时）
- [ ] 不可逆技术决策已记 ADR（含备选与代价）
- [ ] 把提示词/配置/脚本外置出代码时，已补 MCP 通道或 `//!` 锚点注释（重跑 `sh scripts/collar-anchors.sh`）

### ④ 过程知识沉淀（仅命中门槛时）
- [ ] 反复踩过的坑或新确立的工程红线已落 `conventions.md` / `troubleshooting.md`（单次偶发坑不入规）
- [ ] `BREAKING` 变更已在 commit message 标 `!` 并写明迁移方式

# 关键约定（强约定清单）

> 这里的每一条都是**踩过坑才总结出来的**。违反即视为缺陷。
> AGENTS.md 的速查表只放一句话摘要 + 链接，完整解释在这里。

---

## 模板约定（示例，落地时替换为真实约定）

### C-001 · 环境差异优先怀疑

- **现象**：代码逻辑正确，但预发环境表现与本地不一致
- **根因**：预发与线上存在配置/数据源差异（详见 [environments.md](environments.md)）
- **结论**：**遇到无法解释的现象，先怀疑环境，再怀疑代码**
- **证据**：见 [environments.md](environments.md)

### C-002 · 外置逻辑必须保留锚点

- **现象**：把提示词/配置迁到平台后，AI 说「我不知道这个 Agent 的具体行为，请去平台修改」
- **根因**：行为逻辑外置出代码，AI 的推理链断裂
- **结论**：任何外置必须同步缝补，见 [context-stitching.md](context-stitching.md)
- **证据**：AI 时代工程纪律铁律

### C-003 · Spec 不自动反向更新

- **现象**：代码与 Spec 不一致
- **根因**：编码过程中发现了更好的方案（这是正常的）
- **结论**：**只输出差异清单交人决策**，禁止 AI 自动把 Spec 改成和代码一致
- **证据**：`collar-specs` 模式 B

### C-004 · 标记未知，而非编造

- **现象**：AI 缺少某个事实（接口行为、历史决策、线上配置）时，直接按「合理猜测」继续写方案或代码
- **根因**：生成式模型的默认行为是给出流畅回答，沉默不是它的本能选项
- **结论**：**事实缺口必须显式标记为「待确认」并发起明确提问**，禁止用猜测填充后继续推进。提问格式：已查过什么 → 差什么事实 → 谁能裁决
- **证据**：架构师 Agent 实践（阿里，2026-09）：人从「替 AI 收集资料」转为「裁决事实缺口」

### C-005 · 验收标准编号，测试点回指

- **现象**：代码改完测试也改了，但没人说得清「测的是哪条验收标准」；spec 里某条验收标准从未被任何测试覆盖，直到上线才暴露
- **根因**：验收标准（人写的意图）与测试点（工程实现）之间没有编号连接，两边各自演化，无法机械核对
- **结论**：**spec §5 验收标准必须编号 `AC-N`**（patch §⑥ 用 `AC-P⟨NNN⟩-N`），
  同目录 `tests.md` 的每个测试点必须回指某条 AC；有 AC 无测试点即视为缺口，登记进 `tests.md` 的「已知缺口」
- **证据**：`docs/specs/_templates/tests.md`；见 [testing.md](testing.md) T-001

### C-006 · 现状文档只写现在时

- **现象**：文档里出现「新增了检查项」「上一版方案是 X」这类改动叙述，
  未来会话的读者没有当时的上下文，无法判断哪句描述的是现状
- **根因**：写作时顺着改动过程叙述（「我做了什么」），而不是陈述结果（「系统现在是什么样」）；
  会话内的指代离开会话就成了悬空引用
- **结论**：**现状类文档（AGENTS.md、各 README、架构视图、tests.md 正文）只写现在时事实**；
  历史叙述只进专门记录过去的模块——changelog（何时改的）、ADR（为何这么选）、
  sunset 与 `_archived/`（下线脉络）。结构门禁 S7 会拦截典型指代词
- **证据**：`scripts/collar-check.sh` S7；2026-09-15 引入

### C-007 · 进度只能经命令推进，不能由 Agent 直接改写

- **现象**：会话声称「这一步已完成」并继续往下走，但状态文件、任务勾选或 AC 状态其实没有对应证据；
  事后从产物上回看，看不出哪一步被跳过了
- **根因**：状态是被 Agent 当作叙述的一部分「顺手改掉」的，而不是由一次真实的状态转移产生；
  Agent 自述的完成度是它对自己工作的描述，不构成状态变更的依据
- **结论**：**状态只能经确定性入口（脚本或 CLI）转移，Agent 不得直接改写状态文件与勾选位**。
  每次转移同时记录：完成时间、触发者、产出的证据（命令输出 / 测试结果 / 差异清单）。
  验收看覆盖范围、失败项与关键结果三项，不看「状态字段是否显示完成」
- **证据**：见 [commit-checklist.md](commit-checklist.md) ⑤「任务未勾完不把状态标已验证」；
  外部依据：腾讯技术工程 90 万行重构实践（CLI 管理进度 + Hook 守卫防篡改），2026-10-16

### C-008 · 只报交付周期总数，分不清该优化哪一侧

- **现象**：门禁越加越多、Agent 执行越来越快，交付周期却只小幅改善；复盘时说不清这段时间究竟省在执行上还是耗在等接手，于是继续往执行侧加约束
- **根因**：周期被当成一个整体指标在管。真实结构是 `周期 = Σ(每轮:执行时间 + 接手等待) + 外部等待`——执行时间归工具链与知识，接手等待归协作安排；只报总数会让两个方向混为一谈，而执行侧通常已经接近下限，继续压它的收益极小
- **结论**：**按轮核算，把执行时间与接手等待分开记账，并区分「卡点」与「悬置」。**
  一轮从人的输入开始，到 Agent 交付、人接手给出下一步输入为止；并行分支只沿决定完结时刻的关键路径计算，不得各分支相加。
  可另记一个零填报的连续性指标 `流动效率 = 流动天 ÷ 流逝天`（当天有任何发言、交付或工具调用即算在动），它衡量活动连续性，不是完工比例。
  静默只作排查入口：先还原最近一次交接（产物交给了谁、缺什么、有无新安排），再判断是已确认障碍的**卡点**（如缺权限使验证无法执行）还是未见接续的**悬置**；只按静默天数触发的模板消息会催错人。
  回执、责任接手、问题解除三态分开记——知晓只是回执，接手才停止催促，解除须有证据。计时对象是**这个问题**，不是这个群
- **证据**：实测编码层人工介入已压到每需求约 0.5 轮，39 个已上线需求四档复杂度周期仍只缩短一到三成；
  流动效率低/中/高三组周期中位约 22/14.5/8 天；261 段静默中「等人回应」占 66%、其中 64% 后来自行恢复（中位 3 天）——**报干预收益前必须先扣掉自然恢复，并设同期未介入的对照**。
  外部依据：天猫技术《数字员工（效能篇）》，2026-10-26

### C-009 · 只报编码提速，等于没报提效

- **现象**：团队加了门禁、加了 Skill、加了自动检查，编码环节明显变快，汇报时拿"生成速度提升 N 倍"作为成果；但需求到上线的周期只小幅改善，甚至因为返工增加而变慢
- **根因**：两笔账没算。一是**验证税**——AI 生成省下的时间要扣掉新增的上下文整理、核验、修正与返工；二是**结构性上限**——编码只占研发总耗时约三成，剩下七成是需求澄清、对齐、联调、返工与部署，即使编码瞬间完成，端到端也只能省那三成（阿姆达尔定律）。只压编码，天花板就在那里
- **结论**：**提效结论只认端到端三项，不认生成速度。**
  报①端到端交付时间、②人工判断与返工成本、③上线缺陷与长期维护成本；三者同时改善才算提效。
  同时按任务类型分档声明预期：隐性决策少、验收直接、生命周期短的日抛型任务（原型、一次性工具）最容易兑现生成收益；系统关联多、需长期维护的任务，净收益取决于系统事实能否进入上下文、变更能否通过独立证据验证。**不得把日抛型任务的加速比当作复杂系统的预期**。
  推论：投入顺序上，先把验证容量与证据链补齐，再扩大自动生成与自动执行的范围——顺序反了，产出会堆在验证队列里
- **证据**：某千人团队两年实测，好的团队提效三成多、差的没有提效，原因是"AI 投入几乎全压在占三成的编码环节，且全以个体为单位、从未以团队为单位"；
  另一团队给出阿姆达尔式结论与"验证税"概念，并引用 Faros AI 逾 1 万名开发者研究与 Sonar 调查（38% 认为评审 AI 代码比评审同事代码更费力）
  外部依据：嘀嗒出行《一个人用 AI 像开挂，团队协作就打架》，2026-10-29；腾讯云开发者《代码秒出，验证排队？AI Coding 的隐性账单》，2026-10-30

### C-010 · 确定性步骤必须代码化，AI 只留推理点

- **现象**：把流程写成详尽的说明让 Agent 逐步执行，实际跑起来漏步骤（写的是 1→2→3→…→9，跑成 1→2→4→7→9），还会出现"某步已完成"但对应工具从未调用的幻觉式完成；流程越长越不可靠
- **根因**：把确定性流程塞进了概率性提示词。每步遵守率 95% 时，74 步全对约 2%，8 步约 66%——可靠性随决策点数量指数衰减，这是数学事实而非模型能力问题。编译重试、分支切换、状态持久化、门禁校验这类操作本来不需要判断，交给模型就是把确定性拖成概率性
- **结论**：**每一步先问"这件事能不能用代码做"，能就不交给 AI。**
  判据：某步骤「AI 做对与做错的结果完全不同」（分支切换、状态持久化、编译门禁、截图与回滚判定），它就是确定性步骤，必须下沉到 CLI 或脚本。
  配套三条：① 流程调度不靠 AI 记忆——CLI 每步输出下一步该走哪条命令的提示；② 跳过校验直接宣告完成时，CLI 前置校验状态后拒绝执行；③ 会话结束由**独立于 AI 的钩子**校验交付契约，不满足则把 AI 拒回去继续工作（钩子本身出错要放行，避免防护机制拖垮工具链）。
  同理，AI 可能"随手填"的每个字段都要有独立于 AI 的检测，矛盾时须书面反驳，否则拒绝交付
- **证据**：实测把 74 个决策点中的 66 个确定性步骤下沉到 CLI 后，AI 只留 8 个推理点，漏步骤率从约 30% 降到 5% 以下，模型未换；
  交付门禁 7 项检查中 6 项有独立交叉验证，防绕过覆盖从 0/7 提到 6/7
  外部依据：淘天集团《让 AI 看得见、判得准、改得对——D2C 从设计稿到三端真机达标的自动化实践》，2026-11-02

### C-011 · 「接口返回成功」不是完成证据

- **现象**：Agent 报告「已验证通过」，依据是接口返回 200 或 code=0；上线后才发现字段含义不对、库状态没变、下游其实失败、异步消息根本没被消费
- **根因**：把「调用成功」当成了「需求实现正确」。这两件事之间隔着业务规则、边界条件、老数据兼容、异步副作用——只看返回值，四种「表面成功」全都能骗过验收
- **结论**：**完成判定按证据强度分层，不以下游返回码为准。**
  取证顺序：链路与异步确认（下游调用、消息消费、日志）> 业务状态验证（配对查询接口、直接查库）> 静态 Review 兜底。只有确实无法联机验证才降到静态层，且必须显式标注「这是读代码的判断，不是实测」。
  同时区分两类受限：**硬阻塞**（需求预期待确认、环境不可用）停下等人；**软失败**（发布失败、日志暂不可读）不停整轮，继续完成变更分析、场景生成与风险标注。能验证的尽量验证，不能验证的诚实标注，**不得把受限项伪装成通过**。
  前置纪律：先确认「能不能验」（环境、编译、发布、接口连通、契约一致），再判断「对不对」——前提不成立时后面全是空转
  完成粒度必须分开统计：**流程跑完 / 提出 MR / 代码合入 / 业务验收通过是四件事**，混成一个「进度」一定高估真实交付；判据取最严那一档（只有合入并通过验收才算完成），并同时记录返工次数、等待时间与人工介入次数。另配一条时效纪律：**代码一变，此前的检查报告即失效**，不能继续用来证明新版本已通过。
  审计与配置核查类任务再补一条入口纪律：**配置仓库展示意图，运行环境展示实际结果**。只读配置会漏掉三类情况——被准入/注入链路改写的配置、由其他仓库或平台工具创建的资源、看起来正确但实际未生效的设置。此类核查必须以运行时的事实源（平台的实际资源清单/生效态）为入口，配置扫描只作为补充；查不清时保留「无法确定」，不得默认判定为安全。
- **证据**：四类表面成功的具体形态（接口成功字段不对 / 写成功库没变 / 主接口成功下游失败 / 异步未消费或日志无副作用）来自真实医疗业务验收实践；
  Gherkin 场景必须人工确认后才执行——预期错了，后续报告更完整也更迷惑
  完成粒度四分与「报告随代码失效」来自腾讯轻量云 LoopForge 实践（InfoQ 采访江露，2026-11-18）：只有合入并通过验收才算交付
  「配置是意图、运行环境是结果」来自 Shopify Overexposed 公网暴露扫描实践（InfoQ 编译，2026-11-21）：改以云资产清单为事实源后无法确定的比例下降约 80%
  外部依据：腾讯云开发者《AI 10 分钟写完代码，你 2 小时还在验？用验收 Agent 补上最后一公里》，2026-11-11

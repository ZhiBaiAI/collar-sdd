# 关键约定（强约定清单）

> 这里的每一条都是**踩过坑才总结出来的**。违反即视为缺陷。
> AGENTS.md 的速查表只放一句话摘要 + 链接，完整解释在这里。

## 模板约定（示例，落地时替换为真实约定）

### C-001 · 环境差异优先怀疑

- **现象**：代码逻辑正确，但预发环境表现与本地不一致
- **根因**：预发与线上存在配置/数据源差异（详见 [environments.md](environments.md)）
- **结论**：**遇到无法解释的现象，先怀疑环境，再怀疑代码**
- **证据**：见 [environments.md](environments.md)

### C-002 · 外置逻辑必须保留锚点

- **现象**：把提示词/配置迁到平台后，AI 说「我不知道这个 Agent 的具体行为，请去平台修改」
- **根因**：行为逻辑外置出代码，AI 的推理链断裂
- **结论**：任何外置必须同步缝补，见 [context-stitching.md](context-stitching.md)
- **证据**：AI 时代工程纪律铁律

### C-003 · Spec 不自动反向更新

- **现象**：代码与 Spec 不一致
- **根因**：编码过程中发现了更好的方案（这是正常的）
- **结论**：**只输出差异清单交人决策**，禁止 AI 自动把 Spec 改成和代码一致
- **证据**：`collar-specs` 模式 B

### C-004 · 标记未知，而非编造

- **现象**：AI 缺少某个事实（接口行为、历史决策、线上配置）时，直接按「合理猜测」继续写方案或代码
- **根因**：生成式模型的默认行为是给出流畅回答，沉默不是它的本能选项
- **结论**：**事实缺口必须显式标记为「待确认」并发起明确提问**，禁止用猜测填充后继续推进。提问格式：已查过什么 → 差什么事实 → 谁能裁决
- **证据**：架构师 Agent 实践（阿里，2026-09）：人从「替 AI 收集资料」转为「裁决事实缺口」

### C-005 · 验收标准编号，测试点回指

- **现象**：代码改完测试也改了，但没人说得清「测的是哪条验收标准」；spec 里某条验收标准从未被任何测试覆盖，直到上线才暴露
- **根因**：验收标准（人写的意图）与测试点（工程实现）之间没有编号连接，两边各自演化，无法机械核对
- **结论**：**spec §5 验收标准必须编号 `AC-N`**（patch §⑥ 用 `AC-P⟨NNN⟩-N`），
  同目录 `tests.md` 的每个测试点必须回指某条 AC；有 AC 无测试点即视为缺口，登记进 `tests.md` 的「已知缺口」
- **证据**：`docs/specs/_templates/tests.md`；见 [testing.md](testing.md) T-001

### C-006 · 现状文档只写现在时

- **现象**：文档里出现「新增了检查项」「上一版方案是 X」这类改动叙述，
  未来会话的读者没有当时的上下文，无法判断哪句描述的是现状
- **根因**：写作时顺着改动过程叙述（「我做了什么」），而不是陈述结果（「系统现在是什么样」）；
  会话内的指代离开会话就成了悬空引用
- **结论**：**现状类文档（AGENTS.md、各 README、架构视图、tests.md 正文）只写现在时事实**；
  历史叙述只进专门记录过去的模块——changelog（何时改的）、ADR（为何这么选）、
  sunset 与 `_archived/`（下线脉络）。结构门禁 S7 会拦截典型指代词
- **证据**：`scripts/collar-check.sh` S7；2026-09-15 引入

### C-007 · 进度只能经命令推进，不能由 Agent 直接改写

- **现象**：会话声称「这一步已完成」并继续往下走，但状态文件、任务勾选或 AC 状态其实没有对应证据；
  事后从产物上回看，看不出哪一步被跳过了
- **根因**：状态是被 Agent 当作叙述的一部分「顺手改掉」的，而不是由一次真实的状态转移产生；
  Agent 自述的完成度是它对自己工作的描述，不构成状态变更的依据
- **结论**：**状态只能经确定性入口（脚本或 CLI）转移，Agent 不得直接改写状态文件与勾选位**。
  每次转移同时记录：完成时间、触发者、产出的证据（命令输出 / 测试结果 / 差异清单）。
  验收看覆盖范围、失败项与关键结果三项，不看「状态字段是否显示完成」
- **证据**：见 [commit-checklist.md](commit-checklist.md) ⑤「任务未勾完不把状态标已验证」；
  外部依据：腾讯技术工程 90 万行重构实践（CLI 管理进度 + Hook 守卫防篡改），2026-10-16

### C-008 · 只报交付周期总数，分不清该优化哪一侧

- **现象**：门禁越加越多、Agent 执行越来越快，交付周期却只小幅改善；复盘时说不清这段时间究竟省在执行上还是耗在等接手，于是继续往执行侧加约束
- **根因**：周期被当成一个整体指标在管。真实结构是 `周期 = Σ(每轮:执行时间 + 接手等待) + 外部等待`——执行时间归工具链与知识，接手等待归协作安排；只报总数会让两个方向混为一谈，而执行侧通常已经接近下限，继续压它的收益极小
- **结论**：**按轮核算，把执行时间与接手等待分开记账，并区分「卡点」与「悬置」。**
  一轮从人的输入开始，到 Agent 交付、人接手给出下一步输入为止；并行分支只沿决定完结时刻的关键路径计算，不得各分支相加。
  可另记一个零填报的连续性指标 `流动效率 = 流动天 ÷ 流逝天`（当天有任何发言、交付或工具调用即算在动），它衡量活动连续性，不是完工比例。
  静默只作排查入口：先还原最近一次交接（产物交给了谁、缺什么、有无新安排），再判断是已确认障碍的**卡点**（如缺权限使验证无法执行）还是未见接续的**悬置**；只按静默天数触发的模板消息会催错人。
  回执、责任接手、问题解除三态分开记——知晓只是回执，接手才停止催促，解除须有证据。计时对象是**这个问题**，不是这个群
- **证据**：实测编码层人工介入已压到每需求约 0.5 轮，39 个已上线需求四档复杂度周期仍只缩短一到三成；
  流动效率低/中/高三组周期中位约 22/14.5/8 天；261 段静默中「等人回应」占 66%、其中 64% 后来自行恢复（中位 3 天）——**报干预收益前必须先扣掉自然恢复，并设同期未介入的对照**。
  外部依据：天猫技术《数字员工（效能篇）》，2026-10-26
